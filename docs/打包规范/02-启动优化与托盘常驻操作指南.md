# SmartBoBo 启动优化与托盘常驻操作指南

> 适用版本：**v0.3.0+**（`packaging/` 脚手架）
> 参考项目：[dsh-float](https://gitee.com/windowsuninstaller/dsh-float)（Python 壳 + dsh 服务 + WebView2，同构形态）
> 关联：`docs/打包规范/01-Windows安装包打包规范.md`（打包体系与问题清单）
> 状态：已实施（2026-10-14）

## 一、背景

v0.2 同事反馈：双击后 **十几秒** 才能看到界面。拆解启动链（见 01 号文档 §11 复盘）：

| 阶段 | v0.2 估计 | 问题 |
|---|---|---|
| PyInstaller onefile 解压 | 1~3s | 每次启动把 ~40MB 解到临时目录 |
| env manifest + dbx 播种 | 1~2s | 两次 Python 冷启动，**每次启动都跑** |
| 品牌补丁 | 1~2s | 每次启动都跑；payload 出厂已打过，纯浪费 |
| 内核起服 | 5~8s | 长杆；且被上面步骤串行挡在后面 |
| WebView 加载 SPA | 1~3s | — |

dsh-float 的结论（其 README/CHANGELOG 实测数字）：这类应用的"快"**不是把服务压到 0 秒**（它冷启动 dsh 仍要 5~6s），而是：

1. **界面先出来**（本地等待页），服务后台就绪后原地跳转；
2. **服务热复用**（端口探测，已监听就直连，跳过冷启动）；
3. 毫秒级抠：短超时单次探测、延迟导入、**目录分发代替 onefile**。

## 二、v0.3 落地的优化（可复制的操作清单）

### 2.1 目录分发代替 onefile（省 1~3s）

`packaging/launcher/build_launcher.py` 去掉 `--onefile`：

```bat
python packaging\launcher\build_launcher.py
:: 产物从单个 SmartBoBo.exe 变为目录：
:: packaging\dist\launcher-dist\SmartBoBo\{SmartBoBo.exe, *.dll, _internal\}
```

NSIS 侧对应改动（`smartbobo.nsi`）：

```nsis
; 安装：整目录平铺到 $INSTDIR
SetOutPath "$INSTDIR"
File /r "${LAUNCHER_DIR}\*"
; 卸载：onedir 要多删 _internal 与 dll
RMDir /r "$INSTDIR\_internal"
Delete "$INSTDIR\*.dll"
Delete "$INSTDIR\*.zip"
```

### 2.2 去掉每次启动的重复劳动

`launcher.py` 规则改为：

| 步骤 | v0.2 | v0.3 |
|---|---|---|
| 品牌补丁 | 每次启动 | **仅首启**（`.bobo-initialized` 刚写入时）；payload 出厂内核已带补丁 |
| env manifest | 每次启动 | **仅当** `dbx-runtime/env-manifest.json` 缺失（后台线程） |
| dbx 播种 | 每次启动 | **仅当** `BoBoData/dbx-runtime/data/dbx.db` 缺失（后台线程） |
| uv sync / pnpm install | 首启 | 不变（幂等标记，非首启 ~0ms 跳过） |

### 2.3 内核先行 + maintenance 不挡路

冷启动顺序从「manifest → dbx → 品牌补丁 → 内核」改为：

```
ensure_profile_deps（同步，非首启为 0ms 探测跳过）
  ├─ maintenance 线程（env manifest / dbx 播种，仅缺失时）  ← 后台
  └─ start_kernel（长杆，立即开工）                        ← 主路径
```

注意：**profile 依赖安装必须同步在内核启动前完成**——内核只 skip 解析失败的 bundle 不会自装，首启若并行装依赖会被内核跳过（v0.2 已踩坑，见 01 文档 P2）。

### 2.4 服务热复用（二次启动秒开的前提）

`probe_service()`：`socket.connect_ex` 单次探测 `127.0.0.1:7075`，**超时 0.08s**。

```python
# dsh-float 实测教训：本机空端口是 WSEWOULDBLOCK，必然等满超时。
# 0.3s 超时白烧 313ms；两处各探一次白烧 636ms。只探一次、超时要短。
```

已监听 → 跳过 uv/pnpm/内核启动，直接 `load_url`。配合 2.5 的托盘常驻，**第二次双击是秒开**。

### 2.5 托盘常驻：关窗不停服，托盘退出才真退出

依赖：`pystray` + `Pillow`（`pip install pystray pillow`，已进 PyInstaller hidden-import）。

行为定义：

| 动作 | 行为 |
|---|---|
| 点窗口 ✕ | **隐藏到托盘**，内核继续运行（`window.events.closing` 返回 False 取消销毁 + `window.hide()`） |
| 托盘左键 / 「显示主界面」 | `window.show()` + `restore()` 瞬时唤醒 |
| 托盘「退出」 | `stop_kernel()`（terminate/kill 内核进程树）→ 销毁窗口 → `icon.stop()` → 进程结束 |
| 卸载 | NSIS 卸载段先 `taskkill /f /t /im SmartBoBo.exe`（托盘模式下窗口关了进程还在，不先杀会文件锁） |

托盘图标用 `docs/bobo.ico`，经 `--add-data` 打进 `_internal/bobo.ico`，运行时 `resource_path()` 定位。

### 2.6 计时打点（优化前后都用数字说话）

`launcher.py` 入口起 `perf_counter`，每条日志带 `+X.XXs` 相对时间，写 `BoBoData/logs/launcher.log`：

```
[TIME] 启动器入口
[TIME] 窗口已创建（splash）
[OK  ] 检测到已在运行的服务，热复用 :7075   ← 热路径
[TIME] WebView 页面加载完成
```

验收方法：看 log 里「窗口已创建」与「WebView 页面加载完成」的差值，即用户感知的"打开耗时"。

## 三、预期效果（本机实测，2026-10-14）

`BoBoData/logs/launcher.log` 打点（v0.3.0 实测）：

| 场景 | 实测 | 说明 |
|---|---|---|
| 冷启动 → **窗口/splash 出现** | **1.55s** | onedir 无解压；用户 1.5 秒内看到界面 |
| 冷启动 → 服务就绪（环境已备好） | **+12.1s**（其中内核 ~7.4s） | kernel 是长杆；首启另加 uv/pnpm ~7s |
| 首启全流程（uv+pnpm+内核） | **13.3s** | pnpm 走热缓存仅 ~3.5s；manifest/dbx 与内核并行 |
| **热复用（托盘常驻中二次双击）** | **0.07s** 探测到并直连 | splash 随即切真页面，体感秒开 |

对比 v0.2「十几秒才能打开」：**感知打开时间 = splash 出现时间（1.5s）**，真页面冷启动 ~12s、热启动秒开。v0.2 同期感知是等完整串行链走完才见窗口。

## 四、构建与验证操作

```bat
:: 1. 重打启动器 + 安装包（payload 未变可只跑 launcher + makensis，见 01 文档 §11.5）
python packaging\launcher\build_launcher.py
packaging\build_installer.cmd

:: 2. 冒烟（headless，不弹窗不启托盘）
packaging\test\install_smoke.cmd packaging\dist\SmartBoBo_0.3.0_x64-setup.exe
```

人工验收清单：

1. 冷启动：装完双击 → splash 秒出 → 数秒后进主界面；
2. **关窗**：窗口消失，任务管理器仍有 `SmartBoBo.exe` + `node.exe`，托盘有菠萝图标；
3. 托盘「显示主界面」：窗口瞬时回来，页面不刷新重连（服务没死）；
4. 再次双击桌面图标：**秒开**（热复用，launcher.log 有「热复用 :7075」）；
5. 托盘「退出」：`SmartBoBo.exe` 与 `node.exe` 全部消失；
6. 卸载：装着（托盘挂着）直接跑卸载 → 进程被清、文件删净、`BoBoData` 保留。

## 五、已知行为与限制

- **端口冲突即"复用"**：若机器上已有别的进程占着 :7075（例如开发机的 `启动.cmd`），打包版会直接连它而不是起自己的内核。dsh-float 同款取舍；如需区分，后续给内核加身份端点再校验。
- **托盘不杀内核 = 内存常驻**：node 内核 + 221 包约几百 MB。这是"二次秒开"的代价，与 dsh-float 一致（其 README 亦明示）。
- 热复用路径**跳过** uv/pnpm/maintenance 检查——假设服务活着则环境完好。若手工删了 venv 又托盘挂着，需托盘退出后再冷启动自愈。
- Windows 通知区域图标可能默认折叠（`Windows 设置 → 任务栏 → 选择哪些图标显示`），首次使用请留意。

## 六、dsh-float 借鉴对照表

| dsh-float 手段 | v0.3 是否采用 | 落点 |
|---|---|---|
| 先出窗口 + 本地等待页轮询 | ✅（已有 splash，保留） | `LOADING_HTML` + boot 线程 |
| 服务端口热复用 | ✅ | `probe_service()` 0.08s 单次探测 |
| 退出不杀服务 | ✅（改为显式托盘退出才杀） | 托盘菜单「退出」+ NSIS 卸载 taskkill |
| onedir 目录分发 | ✅ | `build_launcher.py` 去 `--onefile` |
| 端口探测短超时/单次 | ✅ | `PROBE_TIMEOUT_S = 0.08` |
| 延迟导入 | ✅ | pywebview/pystray/PIL 均在函数内 import |
| 分阶段计时打点 | ✅ | `elapsed()` + launcher.log |
| 双 WebView `lift()` 秒切 | ❌ 未采用 | tkwry 专属；内存代价大 |
| `--noupx` | n/a | 我们不用 UPX |
