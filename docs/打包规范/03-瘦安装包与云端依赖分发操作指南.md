## 七、安装实测问题与修复（2026-10-14，测试目录 `E:\垃圾箱\BoBo安装测试`）

按你反馈"安装依然有很多问题"，在指定测试目录完整跑了一遍装→启→认证→热复用，发现并修复：

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 双击后自动跳转到系统浏览器 | 内核 `dsh web` 默认 `openBrowser=true`，会自己弹默认浏览器 | 内核命令加 **`--no-open`** |
| 2 | 应用窗口里是 401 空白（"authentication required"） | 浏览器会话认证：裸 URL 无 `?token=` 一律 401；窗口之前 load 的是裸地址 | ① Node 预加载 `capture-url.cjs` 拦截内核打印的 `dsh web: …?token=`；② stdout 解析兜底；③ 窗口只加载**认证地址**；④ 认证地址落盘 `BoBoData/.dsh/web-url.txt` 供热复用 |
| 3 | token 捕获落空（等到 5s 放弃） | `announceReady` 在插件全量加载后才打印，比端口监听晚 ~10s | 就绪后**最多再等 60s** 捕获 token，拿到才 load_url |
| 4 | pnpm/node/python 子进程弹黑框 | GUI 进程拉起控制台子进程缺 `CREATE_NO_WINDOW` | 所有 `subprocess` 加 `creationflags=CREATE_NO_WINDOW` |

**修复后实测**（同一测试目录，干净重装）：

```

→ 内核起服 + 捕获 token（约 44s）
→ 窗口加载 http://127.0.0.1:7075/?token=… → 303 Set-Cookie → 200 HTML 41KB ✓
→ 关窗托盘常驻 → 再双击 → 热复用 2s 直连（读落盘认证地址）✓
```

**新文件**：`packaging/launcher/capture-url.cjs`（Node 预加载，PyInstaller `--add-data` 打进 `_internal/`）。

## 八、工作区无法选择问题与修复（2026-10-14）

**现象**：装机后打开界面，点击"选择工作区"无法完成选择（尤其无法浏览添加新文件夹）。

**根因链**：
1. 打包启动器用 `CREATE_NO_WINDOW` 隐藏拉起内核（修终端弹窗，必要且正确）；
2. 内核的目录选择器在 Windows 上默认选 **native** 后端（`dsh-host-directory-picker-auto` → Win32 文件夹对话框，子进程 `worker.cjs`）；
3. 隐藏控制台进程弹出的原生对话框**无法可靠置顶/显示**，用户点击后无反应；
4. 更隐蔽的坑：cordis patch **不能改已有行的 `name`**（mismatch 直接 skip），也不能用裸 `- id:` 新增行——新增必须 `- insert:`。

**修复**（`build_payload.py` 的 `force_browse_picker()`）：
```yaml
# 禁用 auto 行
- id: directory-picker
  disabled: true
# insert browse 对（服务端列目录 + 应用内文件浏览器，不依赖宿主显示器）
- insert:
    - id: directory-picker-browse-host
      name: '@deepseek-ai/dsh-host-directory-picker-browse'
    - id: directory-picker-browse-ui
      name: '@deepseek-ai/dsh-client-ui-directory-picker-browse'
```

**已装旧版的补救**（不重装）：把上述块追加到
`<安装目录>\BoBoData\.dsh\profiles\web\cordis.patch.yml` 末尾，重启应用。

**验证**：重启后 `__DSH_BOOT__` 中出现 `dsh-client-ui-directory-picker-browse`、不再有 `directory-picker-native`；点击选择工作区弹出应用内文件浏览器面板。

### 9.3 本轮踩坑与规避（按发现顺序）

#### 坑 1：内核自动开浏览器 + 窗口 401

- **现象**：双击后跳到系统浏览器；应用窗口白屏 401。
- **原因**：`dsh web` 默认 `openBrowser=true` 自己弹浏览器；窗口 load 裸 URL 无 `?token=` 被浏览器会话认证拒绝（401）。
- **规避**：内核命令加 `--no-open`；用 Node 预加载 `capture-url.cjs` 拦截内核 `console.log` 抓 `dsh web: …?token=`；窗口只加载认证地址；落盘 `BoBoData/.dsh/web-url.txt` 供热复用。
- **教训**：**dsh web 的 token 是进程级的**——热复用别的进程起的服务时拿不到对方 token，只能退回裸 URL（可能 401）。自家托盘常驻场景（同进程）用落盘 URL 没问题。

#### 坑 2：token 捕获超时

- **现象**：端口就绪后 6 秒仍拿不到 token。
- **原因**：`announceReady` 在插件全量加载后才打印，比 TCP 监听晚 10s+。
- **规避**：服务就绪后**最多再等 60s** 轮询认证地址文件，拿到才 `load_url`。

#### 坑 3：终端黑框

- **现象**：pnpm/node/python 子进程各弹一个控制台。
- **原因**：GUI 进程（`--windowed`）拉起控制台子进程，Windows 默认新建控制台。
- **规避**：所有 `subprocess.Popen/run` 加 `creationflags=CREATE_NO_WINDOW`。
- **教训**：改 `--windowed` 不会自动隐藏子进程控制台，**每个** spawn 点都要显式加标志。

#### 坑 4：工作区无法浏览选择

- **现象**：点"选择工作区"无反应（原生对话框不弹）。
- **原因**：隐藏内核（坑 3 的修复）导致 native Win32 对话框无法置顶。
- **规避**：模板强制 `directory-picker = browse`（应用内文件浏览器）。
- **连带发现的 cordis patch 语义坑**：
  1. **不能改已有行的 `name`**——name mismatch 直接 skip（静默）；
  2. **不能用裸 `- id:` 新增行**——那是覆盖语义；新增必须 `- insert:`；
  3. 禁用行用 `- id: X` + `disabled: true`（不带 name）。
- **教训**：隐藏进程 + 依赖宿主显示器的功能（原生对话框/托盘气泡）天然不兼容，打包时要换成纯应用内实现。

#### 坑 5：pnpm.exe 垫片

- **现象**：`WinError 216`（版本不兼容）。
- **原因**：`shutil.which("pnpm")` 在 Windows 命中 npm 的 133 字节 `pnpm.cmd` 垫片。
- **规避**：随包 pnpm 必须校验 **>1MB 且 MZ 头**；禁止 which 兜底。

#### 坑 6：cordis patch 语义（汇总）

| 操作 | 写法 | 错误写法（会静默失败） |
|---|---|---|
| 覆盖已有行的 config | `- id: X` + 新 config（不带 name） | 带 name 且 name 不同 → skip |
| 禁用已有行 | `- id: X` + `disabled: true` | — |
| 新增行 | `- insert:` + 子列表 | 裸 `- id: X` + name（不生效） |

## 十、v0.4.2：双击"没反应"问题与修复（2026-10-14）

### 10.1 现象与根因

用户反馈：双击 `SmartBoBo.exe` 打不开软件。

**实际排查**：进程活着、窗口句柄存在、服务正常（401）——应用没坏，是**首次启动的前 ~30 秒完全没有窗口**：

```
旧 main() 时序：
+0s    开始下载 311MB 托管依赖（无窗口！）
+29s   下载完 → uv sync → 才进 run_gui() 创建 splash
+46s   服务就绪
```

根因：`main()` 在 `run_gui()` **之前**同步执行 `ensure_managed_deps` + `uv sync`（为品牌补丁需要 node）。真实网络下下载 311MB 可能耗时数分钟，期间用户双击后**看不到任何界面**，误以为软件打不开。

### 10.2 修复（v0.4.2）

**原则：窗口必须先出来，重活全部进 boot 线程。**

1. `main()` 只做毫秒级工作：定位路径、写日志、首启模板实例化（本地复制），然后立即 `run_gui()`；
2. 品牌补丁 / uv sync / 托管依赖下载全部移入 `boot_runtime()`（由 GUI 的 `boot_thread` 在 splash 之后调用），进度经 `boboStatus()` 显示在 splash 上；
3. 品牌补丁改用独立标记 `.dsh/.bobo-branded`（模板实例化标记 `.bobo-initialized` 在 main 里就写了，不能再当"是否跑过补丁"的依据）。

### 10.3 实测（覆盖启动器到既有安装）

```
+0.04s  窗口/splash 出现
+1.93s  WebView 加载完成
+2.11s  后台：brand patch / 依赖检查 / 内核启动并行
```

**双击 → 窗口可见：1.51 秒**（旧版同场景 29 秒）。

### 10.4 经验

- **GUI 应用的铁律：任何可能超过 1 秒的工作都不能放在窗口创建之前**。首启下载、包管理器、解压都算。
- PyInstaller `--windowed` 只是不出控制台，不解决"点了没反应"——用户感知的"打开"= 窗口出现时间，不是进程启动时间。
- splash 不只是装饰：它是首启长流程的**进度容器**，重活必须挂到它的状态更新回调上。
- 首启模板实例化（本地复制+文本替换）实测 <0.1s，可以留在 main 同步做；任何网络/IO 大活都不行。

### 10.5 分发

- 安装包：`http://www.smartbobo.cn/BoBo-setup/releases/SmartBoBo_0.4.2_x64-setup.exe`（42MB）
- 已装 v0.4.1 的用户：可只替换安装目录下的 `SmartBoBo.exe` + `_internal\`（启动器热更新），或重装。

## 十一、v0.4.3：新建会话失败（插件 never started）与修复（2026-10-14）

### 11.1 现象

点"选择工作区"→ 新建会话时报错：

```
新建会话失败：agent-preset/invalid:
  tool-acquisition (.../bobo/tool-acquisition/lib/index.js): never started
  command-skill-model (...): never started
  tool-market (...): never started
```

### 11.2 根因

三个 bobo 自有插件（依赖 `tools`/`commands` 服务）**模块加载失败**，cordis 标记为 never started。

加载失败的真实原因（Node 复现）：

```
Cannot find package '@deepseek-ai/cordis' imported from .../bobo/node_modules/@deepseek-ai/dsh-tools/lib/index.js
Cannot find package '@deepseek-ai/dsh-typert-protocol' imported from .../bobo/node_modules/@deepseek-ai/dsh-llm/lib/index.js
```

**传递依赖缺失**：打包时从内核复制了 8 个包到 `bobo/node_modules`（zod/schemastery/dsh-tools/dsh-llm…），但这些包自己的 `dependencies`（cordis、dsh-typert-protocol、dsh-brand、dsh-util-values…）没复制。开发机靠 ensure-deps 的 junction 指向内核整棵 node_modules 解析；打包版没有这条链。

### 11.3 修复

启动器在内核下载完成后，建一个 **junction**：

```
runtime/node_modules  →  runtime/dsh/node_modules
```

Node 的模块解析从 `bobo/*/lib` 向上走：`bobo/*/lib` → `bobo/node_modules`（8 个直接依赖）→ **`runtime/node_modules`（junction → 内核全量包）**。传递依赖全部命中。Windows junction 不需要管理员权限（`_winapi.CreateJunction`）。

实测：junction 建立后 `require('./bobo/tool-acquisition/lib/index.js')` / `command-skill-model` 均 OK，启动日志零失败。

### 11.4 经验

- **复制单个 npm 包 ≠ 复制它的依赖子图**。从平铺的 pnpm/node_modules 里抠几个包出来，必须连传递依赖一起，或者给它们一条能解析到全量仓库的路径。
- 打包版布局和开发机的本质差异：开发机 `bobo/node_modules` 的 junction 指向**绝对路径**的内核；打包版内核是首启下载的相对路径。junction 是把"内核全量包"暴露给"应用插件"的最轻量桥。
- 以后凡是"从内核抠包给应用侧用"，都要过一遍该包的 `dependencies` 传递闭包，或直接 junction。

## 十二、v0.4.4：托盘"退出"点不动的修复（2026-10-14）

### 12.1 现象与根因

托盘菜单点"退出"，进程不退（窗口已关、内核已死，主进程仍挂着）。

两个叠加原因：

1. **pystray 回调线程被阻塞**：`on_quit` 里同步调 `stop_kernel()`（内部 `proc.wait(timeout=10)`）。pystray 的菜单回调跑在它自己的消息循环线程上，这里一阻塞，后面的 `icon.stop()` 根本轮不到执行。
2. **`webview.start()` 不返回**：窗口此前已被"关闭→隐藏"（`closing` 事件 return False 取消销毁）。托盘退出时再 `destroy()` 一个隐藏的 EdgeChromium 窗口，主消息循环经常挂住不退。最终表现：托盘图标可能消失了，但 `SmartBoBo.exe` 还在任务管理器里。

### 12.2 修复

```python
def on_quit(icon, item):
    _SHUTDOWN.set()
    # 内核终止放后台线程——绝不在托盘回调里做 proc.wait
    threading.Thread(target=stop_kernel, kwargs={"timeout": 5}, daemon=True).start()
    for w in webview.windows: w.destroy()
    icon.stop()
    # 宽限 3s 后强制结束——托盘退出是用户显式指令，不需要等 Python 清理
    threading.Thread(target=_force_exit, args=(3,), daemon=True).start()

def _force_exit(grace=3.0):
    time.sleep(grace)
    os._exit(0)
```

### 12.3 经验

- **托盘/系统回调里禁止做阻塞等待**（进程 wait、网络、大 IO）——一律丢后台线程。
- pywebview 的隐藏窗口 destroy 后 `webview.start()` 可能永不返回；桌面应用的"退出"按钮应该有 **`os._exit` 兜底**，不要依赖主循环自然退出。
- `os._exit` 跳过 finally/atexit——所以内核终止必须在它之前已排入后台线程执行。

- 已装旧版：替换 `SmartBoBo.exe` + `_internal\` 即可（本修复只动启动器）。

## 十三、v0.5.3：预设分层（内置 4 个 / 选装 8 个）与下载源切换（2026-10-15）

### 13.1 预设分层

**产品定义**：安装包只内置 **dsh 内核自带的四个模式**——标准（standard）、ptc、极简（minimal）、创造（cordis）；我们自研的 **8 个自定义预设全部改为市场选装**。

| 分层 | 来源 | 加载方式 |
|---|---|---|
| 内置 4 模式 | `dsh-web-app/presets/{standard,ptc,minimal,cordis}.patch.yml`，随内核 bundle patch 加载 | 内核自带，**不进 payload 模板** |
| 选装 8 预设 | crawl / reverse / workflow / report / empirical / modeling / review / experiment | 市场（`/presets/index.json`）安装到 `.agent-presets/`，由 `preset-includes.mjs` 启动时挂载 |

**实现**（`build_payload.py`）：
1. `build_template()` **不再复制 `.dsh/.agent-presets`** 进模板（8 个自定义预设出包）；
2. `set_default_preset()` 把 profile 的 `selectedDefault: report → standard`（report 不再随包，避免默认选中空预设）；
3. `preset-includes` 插件保留——用户从市场装预设后仍能挂载。

**收益**：payload 44.6MB → **40.4MB**，安装包 42.4MB → **40.5MB**；8 个预设按需从市场拉（单个 10–55KB）。

### 13.2 下载源：域名 → 服务器 IP

**背景**：`www.smartbobo.cn` 被阿里云以"未备案"403 拦截（Beaver），首次启动 5 项托管依赖全部下载失败 → 应用起不来（日志：`托管依赖未就绪，无法启动内核`）。

**处理**：
1. 服务器侧：bobo-market nginx 的 **default_server**（IP Host 访问）增加 `location /BoBo-setup/ { root /; }`——IP 直连可出文件（外网实测 manifest 200、大文件 206 断点续传正常）；
2. 启动器：`DEPS_BASE_URLS` 首位改为 `http://47.102.138.180/BoBo-setup/deps`，域名源降为备选（备案通过后挪回第一位即可）。

**教训**：未备案域名 + 大陆机房 = 网络层拦截，**控制台里没有开关可配**（不是普通 WAF 白名单问题）。域名分发方案必须先过备案，否则 IP+sha256 是唯一可用通道——完整性本来就靠 sha256，HTTP 可接受。

- `manifest.json`（app v0.5.3 + 8 项 deps sha256）→ `/BoBo/BoBo-setup/deps/`

## 十四、v0.5.4：隐私剥离 + 内置浏览器修复 + 数据出 C 盘（2026-10-15）

### 14.1 opencode_go_ai 提供商信息剥离

**需求**：安装包不得包含用户的 `opencode_go_ai` 模型提供商私有信息（本地网关 `127.0.0.1:9355`、完整模型列表、`OPENCODE_GO_AI_API_KEY` 环境变量名、默认模型指向）。

**实现**（`build_payload.py` → `strip_opencode_provider()`）：
- **保留** `llm-pi-ai` 覆盖行，但 `providers` 只留空壳 `providers: {}`——用户在应用内「模型设置」自配 provider；
- **删除** `agent-default-model` 整个覆盖块（它指向 opencode-go-ai / longcat）。

**验证**：模板 grep 无 `opencode` / `OPENCODE` / `9355` / `longcat`；安装后实例化 profile 同样干净。

### 14.2 内置浏览器（itab）修复——后台静默下载

**根因**：首启只 `uv sync`（Python 包），从未执行 `cloakbrowser install`（~200MB 隐身 Chromium）。无浏览器二进制 → cloakserve 起不来 → 面板到不了 live 态 → 永远看不到 itab。

**实现**（按用户要求：不阻塞首启，进对话界面后再下）：
1. 窗口 `load_url` 成功（用户已进入对话界面）后，启动后台线程 `_bg_cloak_install()`；
2. 先 `cloakbrowser info --quick` 检查 `BoBoData/cloakbrowser` 是否已有二进制，有则跳过；
3. 无则静默 `cloakbrowser install`（30min 超时），输出追加到 `BoBoData/logs/first-run.log`；
4. 失败不阻断应用——面板保持离线态（自带重试），重启后会再次触发检查。

**下载源**：官方 `cloakbrowser.dev`（带 Ed25519 签名校验，不宜转存我们服务器）。大陆可达性是已知风险；失败时面板有离线提示。
